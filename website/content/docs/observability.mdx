## Logging

`fx.log_info(...)`, `log_debug`, `log_warning`, `log_error` write to the loggers in
`CurrentLoggers`, skipping entries below `MinimumLogLevel` (`INFO` by default). Annotations and
log spans add context to every entry inside an effect.

<include meta='title="log_entries.py"'>../../snippets/observability/log_entries.py</include>

`logger.layer([...])` replaces the loggers: `console_pretty()` (a function, taking options),
`console_logfmt`, `console_json`, `batched(...)`, your own `fx.Logger.make(...)`, or `logger.to_logging("app")` to hand entries to
the standard library's `logging`.

## Tracing

`eff.with_span(name)` runs an effect inside a span; `@fx.fn("name")` does the same for every call
of a function. Spans nest across forked fibers, and logs inside a span become its events.

The name also labels the function in a failure's trace. A failure logged from inside a plain
`@fx.fn` reads `at Effect.fn (app.py:12)`, the name Effect gives an unnamed `Effect.fn`;
`@fx.fn("check_urls")` makes it `at check_urls (app.py:12)`, and adds the span.

<include meta='title="tracing.py"'>../../snippets/observability/tracing.py</include>

The native tracer keeps spans in memory. To export them, install the OpenTelemetry bridge
(`pyfect-dev[otel]`) and provide `otel.sdk.layer(otel.sdk.Configuration(...))`. Its
`resource` names the service; each signal is on once it has somewhere to go: spans with a
`span_processor`, metrics with a `metric_reader`, logs with a `log_record_processor`. The
providers flush and shut down when the layer is released, so spans still buffered when the
program ends are sent.

<include meta='title="otel_sdk.py"'>../../snippets/observability/otel_sdk.py</include>

To watch spans live in the Effect DevTools instead, provide `devtools.layer()` (see
[DevTools](/docs/devtools)).

In production the processor is usually `BatchSpanProcessor(OTLPSpanExporter())` from
`opentelemetry-exporter-otlp`, with `PeriodicExportingMetricReader(OTLPMetricExporter())` for
metrics.

## Exporting over OTLP

`pyfect.observability` has Effect's own OTLP/HTTP exporters, which need no extra:
`otlp.layer_json(base_url=..., resource=...)` (or `layer_protobuf`) exports logs, metrics and
spans to `/v1/logs`, `/v1/metrics` and `/v1/traces` through the `HttpClient` you provide. Logs
go out a second after the first one is buffered and spans five seconds after, or as soon as
1,000 are waiting; metrics every ten seconds. An exporter with nothing buffered keeps no timer. `otlp_exporter.Flusher` exports everything now, and
releasing the layer sends what is left, waiting up to three seconds.

<include meta='title="otlp_exporters.py"'>../../snippets/observability/otlp_exporters.py</include>

Transient failures are retried three times, honouring a 429's `Retry-After`; any other failure
drops the batch and pauses that exporter for a minute; the first item pushed after the minute
ends the pause. `otlp.layer_from_config()` reads the standard `OTEL_*` variables
(`OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_TRACES_EXPORTER=otlp`, ...)
and installs nothing unless a signal is switched on. In `OTEL_RESOURCE_ATTRIBUTES` keys and
values are trimmed and percent-decoded once, and `key=` keeps an empty value; malformed
percent-encoding is a defect here, while the OpenTelemetry bridge's
`otel.resource.layer_from_env()` logs a warning and drops the variable. Unlike `layer_json`, it needs an encoding
as well as the `HttpClient`: provide `otlp_serialization.layer_json` (or `layer_protobuf`).
`otlp_proxy.layer(base_url=..., headers=...)` mounts the same routes on your `HttpRouter` and
forwards browser exports to the collector, adding the credentials on the server.

## Metrics

Metrics are descriptions: `counter`, `gauge`, `histogram`, `summary`, `frequency`, `timer`.
`track`, `track_errors` and `track_duration` update one as an effect ends.

<include meta='title="metrics.py"'>../../snippets/observability/metrics.py</include>

`metric.prometheus_format()` writes the registry in the Prometheus text format for any HTTP
framework to serve. `pyfect.http.prometheus.layer_http()` is that route on `pyfect.http`'s router, at
`/metrics` unless you pass `path=`.

A `timer` records **milliseconds**, as Effect's does, and the Prometheus text leaves out its
`time_unit` attribute, so the name is the only place the unit can show: name a timer
`..._milliseconds` (`checkout_milliseconds_sum 51521` is 51.5 seconds). For Prometheus's
convention of seconds, pass a `histogram` to `track_duration` with a function from the
`Duration` to what it records, as in Effect
(`fx.sleep("10 millis").track_duration(metric.histogram("checkout_seconds", boundaries=[1.0]), duration.to_seconds)`).

## Profiling fibers

`cProfile` sees the fiber loop calling steps, so the time of every fiber lands in the same few
runtime functions. `pyfect.fiber_profiler` counts fibers instead. A fiber runs in turns, each on
one thread, until it waits or yields, and `fiber_profiler.profile()` times every turn with that
thread's CPU clock and the wall clock. When the block ends, its report has the time per fiber id
(`report.fibers`) and per span name (`report.spans`, keyed by the fiber's innermost span when the
turn ended, `None` outside every span), each a `FiberTime(cpu_ns, wall_ns, turns)`.

Times are exclusive: when a fiber's turn wakes another fiber on the same thread and that fiber
runs at once, nested in the turn, its time is its own. The profiler watches only the start and
return of `Fiber._run` through `sys.monitoring`, so it costs nothing while no profile runs and
two callbacks a turn while one does, however many steps the turn takes. In
[`benchmarks/fiber_profiler.py`](https://github.com/tylergibbs1/pyfect/blob/main/benchmarks/fiber_profiler.py)
a turn costs about 1.2 to 1.6 µs more on CPython 3.13, 3.14 and 3.14t, and with the profiler
imported but off every workload ran within noise of not importing it:

| Workload | Turns | Off | On |
| --- | --- | --- | --- |
| one fiber, 200k `map` steps | 199 | 97.8 ms | within noise |
| 20k forks, each joined | 40k | 104.5 ms | +46% (3.13: +50%, 3.14t: +51%) |
| two fibers trading 100k values through queues | 200k | 1.41 s | +19% (3.13: +22%, 3.14t: +19%) |

So a program whose turns do real work hardly notices it, while one made of turns of a step or
two, the second and third rows, pays for each. One profile runs at a time, across every
thread; another raises `ProfilerBusyError`.

## Reporting errors

An error reporter hands failures to an error tracker such as Sentry. `eff.with_error_reporting()`
sends the cause of a failure of `eff` to the reporters in `CurrentErrorReporters`, then fails
with it as before (`defects_only=True` reports only causes with a defect), and
`error_reporter.report(cause)` sends one cause. There are no reporters by default.
`error_reporter.layer([...])` installs some, replacing the current ones unless you pass
`merge_with_existing=True`. HTTP servers and `HttpApi` handlers report the failures they
turn into responses, so installing the layer is all a server needs.

`error_reporter.make(f)` builds a reporter that calls `f` with one `Report` per typed error
or defect: `error` as an exception, `severity`, `attributes`, the `cause`, the `fiber` and a
`timestamp`. It skips interruptions, and causes and errors it has already reported, so an
error passing several reporting boundaries is reported once. An error sets how it is
reported through class attributes: `report_ignored = True` for expected failures such as a
declined card, `report_severity` (a `LogLevel`; `INFO` otherwise) and `report_attributes`.
