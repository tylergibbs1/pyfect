`pyfect.sql.pg` runs on psycopg 3; install the `pyfect-dev[pg]` extra. psycopg needs the
libpq C library: slim Docker images leave it out, so install it there (`apt-get install libpq5`)
or add `psycopg[binary]`, which bundles it (not built for free-threaded Python). `pg.layer` provides
both `PgClient` and `SqlClient`, so the code from the [SQL guide](/docs/sql) runs unchanged on
PostgreSQL. `PgClient` adds what only PostgreSQL has: `json`, `listen` and `notify`.

The snippets on this page read the server's URL from `DATABASE_URL`:

```bash
DATABASE_URL=postgres://user:password@localhost:5432/app python connect.py
```

## Connecting

`PgPoolConfig` holds the URL (a `Redacted`, so it never shows up in logs), the pool's size
and timeouts, and the session settings. `pg.layer(config)` opens connections as statements
need them and closes them when the layer's scope closes. To read the settings from the
environment instead, use `pg.layer_config({"url": fx.config.redacted("DATABASE_URL")})`.
`sql.pool_stats` gives a `PoolStats` snapshot of the sessions (idle, used, pending, `min`,
`max`); a `make_client` client always reports its one session as used.

Put the user name in the URL (`postgres://app@db:5432/app`) or in `PgPoolConfig(username=...)`.
Without one, the client falls back to the `USER` (or `USERNAME`) environment variable, and
`PGUSER` is not read, as in Effect's PostgreSQL client. Most Docker images set no `USER`, so
there a URL like `postgresql:///app` fails every connection with `No username configured`.

Statements use the same `{}` placeholders as every `SqlClient`. Three things are specific to
PostgreSQL or easy to miss:

- `sql.json(value)` binds a value as `jsonb`. Reading a `json` or `jsonb` column gives the
  parsed value back.
- `sql.literal("...")` is trusted SQL text, spliced in as written. Its argument is a
  `LiteralString`, so pyright rejects text built at runtime.
- `sql.unsafe(text, params)` takes text built at runtime, and its parameters go to
  PostgreSQL's own placeholders, `$1`, `$2` and so on, not `{}`.

## Streaming rows

A statement's `.stream` is its rows as a `Stream`, read from PostgreSQL as the stream is
pulled, so an export of millions of rows never holds them all in memory. The stream holds one
session until it ends. Ending it early, with `take` or by interrupting it (a client that
hangs up on a streamed HTTP response, for example), cancels the query in PostgreSQL.

## Timestamps and time zones

A `timestamptz` column comes back as an aware `datetime` in the session's `TimeZone`, which
is the server's setting unless the pool sets one. Effect's driver gives a JavaScript `Date`,
an instant with no zone, so decode the column the way Effect decodes a `Date`: with
`S.DateTimeUtcFromDate`, which takes an aware `datetime` in any zone and gives it in UTC.
`S.DateTimeUtc` takes only a `datetime` that is already in UTC, so on a server whose zone
isn't UTC it rejects every row. Setting `startup_parameters={"TimeZone": "UTC"}` on the pool
makes the values UTC as well.

## Records

An anonymous record, `ROW(1, 'a')` or `(a, b)`, comes back as a tuple of its fields, each
read as a column of its type would be: `SELECT ROW(1, 'a', NULL)` gives `(1, "a", None)`, and
records nest inside records and arrays. To read the field types, the client asks PostgreSQL
for the statement's results in binary. A field whose type has no binary loader reads as
UTF-8 text, so enums and `citext` give strings, while a binary layout such as `point` fails
with a `SqlError` naming the type's OID: cast that field to `text`, or register a binary
loader for it in `types` (a psycopg `AdaptersMap`). A named composite type
(`CREATE TYPE pair AS (...)`) is not anonymous and still reads as its text, `"(1,a)"`.

Binary results apply to the whole statement, so a statement keeps text results when another
of its columns would read differently in binary: a type with no binary loader (`regclass`),
`float4` (whose binary value is the exact float, `1.100000023841858` for `1.1`), or a type
`types` gives only a text loader. Its records then read as strings, every field a `str`.

## Errors and traces

A failed statement is a `SqlError` whose `reason` comes from the SQLSTATE, as in Effect's
driver: `UniqueViolation` carries the name of the constraint it broke, and any other
integrity violation (a foreign key, a `CHECK`, an exclusion constraint) is a
`ConstraintError`, which, as in Effect, does not. To tell such constraints apart, read the
driver's error in the reason's `cause`: psycopg's `cause.diag.constraint_name` and
`cause.sqlstate`.

Each statement's span records `db.namespace`, `server.address` and `server.port` from the
config's `database` (else `username`, else `postgres`), `host` (else `localhost`) and `port`
(else 5432), as Effect's driver does. They are not read from `url`, so a client configured by
URL alone reports the defaults; give `database` and `host` as well, or add the attributes you
want with `span_attributes`.

## LISTEN and NOTIFY

`sql.listen(channel)` runs `LISTEN` and succeeds once PostgreSQL has confirmed it. It gives a
`Dequeue[Notification, SqlError]` with every notification sent on the channel after that.
The listener holds its own session until its `Scope` closes, so `listen` needs a `Scope`:
here `fx.scoped` around the program. Keep that scope inside the client's layer
(`fx.scoped(program).pipe(fx.provide(layer))`): closing the layer waits for the pool's
sessions to come back, so with the scope outside it
(`fx.scoped(program.pipe(fx.provide(layer)))`) the program never ends, as in Effect. If the session fails, the queue fails with the
session's error. If more than `capacity` notifications (default 1024) are left untaken, the
queue fails with an error saying the listener fell behind.

`sql.notify(channel, payload)` sends one. Inside a transaction, wrap it in
`sql.after_commit(...)`: it then runs only if the transaction commits, so a listener never
hears about a write that was rolled back. `after_commit` takes an effect that can't fail,
so handle the notify's `SqlError` there (here it's logged).

Call `listen` before the first read of the state it reports on: a change committed between
the read and the `LISTEN` would otherwise go unnoticed. The other side of that order is that
the queue can then hold notifications older than the state you read: one sent between the
`LISTEN` and the read is delivered after it. So drop every notification that isn't newer
than what you read, by comparing a version or sequence column, as the snippet does with
`row` (it drops `1:500`).

## Migrations

`pg.migrator` works like the [SQLite migrator](/docs/sql#migrations), and `migrator.layer`
runs the migrations when the layer is built. With `schema_directory`, it also writes the
schema and the migrations table to that directory with `pg_dump`. That's why the layer needs
the platform services, even when it doesn't dump anything.
