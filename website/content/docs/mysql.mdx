`pyfect.sql.mysql` runs on asyncmy; install the `pyfect-dev[mysql]` extra. `mysql.layer`
provides both `MysqlClient` and `SqlClient`, so the code from the [SQL guide](/docs/sql)
runs unchanged on MySQL.

The snippet on this page reads the server's URL from `DATABASE_URL`:

```bash
DATABASE_URL=mysql://user:password@localhost:3306/app python connect.py
```

## Connecting

`MysqlClientConfig` holds the URL (a `Redacted`, so it never shows up in logs) or the
separate `host`, `port`, `database`, `username` and `password`, and the pool's size and
connection lifetime. `connect_options` passes anything else to the driver; with a URL it is
ignored, as in Effect, and the URL's query takes mysql2's `ssl` object
(`?ssl={"rejectUnauthorized":true}`, with `ca`, `cert` and `key` as PEM text) and
`connectTimeout` in milliseconds. To read the
settings from the environment, use `mysql.layer_config({"url": fx.config.redacted("DATABASE_URL")})`.

Statements are prepared on the server and cached per connection. Set
`disable_prepared_statements=True` for servers or proxies that don't support them; the
values are then escaped into the text. A few things work differently than on SQLite and
PostgreSQL:

- MySQL has no `RETURNING`. A statement that changes rows gives no rows; its `.raw`
  result is a `ResultSetHeader` with `affected_rows` and `insert_id`. `.raw` is typed `object`,
  as Effect's is `unknown`, because the same statement API can also give rows or a list of
  results, so read it with `isinstance(header, mysql.ResultSetHeader)`.
- `sql(...).unprepared` can run several statements separated by `;`, and gives a list
  with each one's result.
- A failure's `reason` comes from MySQL's error number: `UniqueViolation` (with the key's
  name as `constraint`), `DeadlockError`, `LockTimeoutError`, `AuthenticationError`, ...
- Interrupting a statement ends it on the server with `KILL QUERY`, sent over a one-off
  connection, and waits for it to stop, so the connection and any transaction on it go on, as
  in Effect. A statement that hasn't stopped within five seconds has its connection closed and
  ended on the server (`KILL`). Ending a stream early reads past a short rest; a statement
  still sending rows after a moment gets `KILL QUERY` too.

## Migrations

`mysql.migrator` works like the [SQLite migrator](/docs/sql#migrations): `migrator.layer`
runs the migrations when the layer is built, recording them in `effect_sql_migrations`.
MySQL commits DDL as it runs, so a migration that fails part way leaves the statements
before the failure applied. The new migrations are recorded before they run, as in Effect's
migrator, and the first DDL statement commits that record too: the failed migration counts
as applied, and the next run skips it. Fix such a database by hand, or keep each DDL
migration to one statement.
