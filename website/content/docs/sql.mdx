`SqlClient` is a service: call it with SQL and it gives back a statement, an effect that
runs on a connection from the client and succeeds with the rows as dicts. `sqlite.layer`
provides one on the standard library's `sqlite3`. For PostgreSQL, install the `pyfect-dev[pg]`
extra and provide `pyfect.sql.pg.layer` instead; the code that uses `SqlClient` stays the
same (see [PostgreSQL](/docs/postgres)). MySQL works the same way with the `pyfect-dev[mysql]`
extra and `pyfect.sql.mysql.layer` (see [MySQL](/docs/mysql)), and SQL Server with the
`pyfect-dev[mssql]` extra and `pyfect.sql.mssql.layer` (see [SQL Server](/docs/mssql)). libSQL
and Turso use `pyfect.sql.libsql.layer` (see [libSQL and Turso](/docs/libsql)), and
ClickHouse `pyfect.sql.clickhouse.layer` (see [ClickHouse](/docs/clickhouse)). Every failure is a `SqlError` whose `reason` says what went wrong (`UniqueViolation`,
`SqlSyntaxError`, `LockTimeoutError`, ...), and `str(error)` shows the message and the driver's
cause.

## Safe statements

Placeholders are `str.format` fields (`{}`, `{0}`, `{name}`), and their values are always
bound parameters. The template is typed `LiteralString`, so pyright rejects SQL text built at
runtime: `sql(f"... WHERE name = '{name}'")` is a type error. Text that has to be built at
runtime goes through `sql.unsafe(text, params)`, which is easy to search for. On Python 3.14
the template can also be a t-string: `sql(t"SELECT * FROM users WHERE id = {user_id}")`.

## A resolver that batches lookups

Code that loads one user at a time, from many fibers, makes one query per user. A
resolver collects the requests made together and runs one query for all of them:
`find_by_id` matches the rows back to requests by id, each request gets its own result,
and duplicates are asked for once. `ordered` and `grouped` cover queries whose results come
back in request order or in groups, and `void` covers writes.

Requests and results are decoded with [schemas](/docs/schema), so a row of the wrong shape
fails with a `SchemaError`. Requests made inside a transaction are batched with requests from
the same transaction only.

### One resolver per tenant

<Callout title="A shared resolver can answer from another tenant's database">

Only the transaction separates batches. Requests made together outside a transaction share
one batch even when each provides a different `SqlClient`, and the batch runs on the first
request's client. A resolver shared by tenants with their own databases gives one tenant
another's rows. Effect's `SqlResolver` does the same and says so.

</Callout>

`execute` runs once for the whole batch, with the services of the request that came first, so
a `SqlClient()` read inside it is that request's client. Give each tenant its own resolver
over its own client, made once with the tenant's client (in the tenant's
[layer](/docs/resources#sharing-by-key), for example) so its requests still batch. When the
tenants share one database, put the tenant in the request instead and filter on it in
`execute`. `RequestResolver.grouped` is no way out: its key replaces the transaction key, so
it would batch requests of different transactions together.

## Transactions

`sql.with_transaction(effect)` runs every statement of `effect` on one connection. It
commits when the effect succeeds and rolls back when it fails, dies or is interrupted, so an
error raised half way through undoes the half that ran. A rollback that fails itself, as on
a lost connection, is a defect, as in Effect, so the transaction then dies and
`catch_tag(SqlError)` doesn't see it. Nested, it uses a savepoint.
`sql.after_commit(effect)` runs `effect` only once the outermost transaction commits.

The SQLite client has one connection, as in Effect, so a transaction holds it from start to
end and every other query on that client waits for it. Keep slow work, such as reading an
upload or calling another service, outside `with_transaction`: read or spool the input
first, then open the transaction to write it.

## Migrations

A migration is an effect that uses `SqlClient`. `migrator.run` creates the
`effect_sql_migrations` table if needed, runs the migrations newer than the last one
recorded, and succeeds with the ids and names it ran. The new migrations run in one
transaction, so if one fails none of them stay applied, and the error is a `MigrationError`.
Two processes starting at once don't run them twice.

`migrator.from_record` takes migrations keyed `<id>_<name>` (`"1_create_users"`) and, as
Effect's `fromRecord`, skips any other key, so a misnamed migration never runs: check the
ids `migrator.run` returns in a test.
`migrator_file_system.from_file_system(directory)` (in `pyfect.sql.migrator_file_system`,
re-exported by each driver's `migrator`) loads `<id>_<name>.py` modules instead, each with its
migration as `default`. `migrator.layer(loader=...)` runs the migrations when the layer is
built, so the app's layer can migrate before anything else uses the database.

## Several databases in one program

Each driver's layer provides two services: its own tag (`mysql.MysqlClient`,
`libsql.LibsqlClient`, ...) and `SqlClient`. Merge two layers and the type checker has nothing
to complain about, since both provide `SqlClient`, but only the last one's stays: as in
Effect, `layer.merge(a, b)` gives `b`'s client. Code that reads `SqlClient` then runs against
whichever came last. Once a program has two databases, read each through its driver's tag,
and give each migrator its own client with `provide_merge`.
