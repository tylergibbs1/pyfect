title: Event log
description: "Event sourcing that works offline: write events to a local journal, replay them through handlers, and sync with a server, encrypted end to end if you like."
---

An event log stores what happened, not the current state. Each write appends an event to a
journal and runs its handler, which updates the read model the program queries. A remote
syncs the journal with a server, so several clients (a phone, a laptop, a browser tab)
apply the same events and converge, even after writing while offline. `pyfect.eventlog`
follows Effect's `effect/eventlog`; import it as a submodule, since `import pyfect` does
not load it.

## Events and handlers

`event.make(tag, primary_key=..., payload=..., success=..., error=...)` declares an
event: its payload schema and a function giving the key its conflicts are found by.
`event_group.empty.add(A).add(B)` collects events, and `event_log.group(group, lambda h:
h.handle(A, fa).handle(B, fb))` registers a handler for each, checked by pyright against
the payload. A handler gets a `HandlerInput`: the decoded `payload`, the journal `entry`
and its `conflicts`, the stored entries of the same event and key that are newer than it,
which a late entry from another client has to respect.

`event_log.layer(event_log.schema(group), handlers)` builds the `EventLog`, which needs an
`EventJournal` and an `Identity`, the owner of the log. `log.write(event, payload)`
appends the event, runs its handler and succeeds with the handler's result;
`write_many([...])` writes several under one lock; `log.entries` reads the journal.

## Rows

`grocery = event_row.make("grocery", key="id", schema=S.Struct(Grocery), key_type=str,
patch_fields=GroceryPatch)` is an event that sets, patches or removes one row:
`grocery.set(row)`, `grocery.patch(key, fields)` and `grocery.remove(key)` give writes for
`write_many`. `key_type` and `patch_fields` (a `total=False` TypedDict of the non-key
fields) let pyright check the key and each patch, as Effect derives them from the schema;
`make` checks `patch_fields` names exactly the non-key fields, and `patch` raises
`EventRowPatchError` for a key field or a field the row does not have.
`event_row.handler(row, set=..., patch=..., remove=...)` turns three callbacks into its
handler, resolving a late entry against the newer ones already stored, so clients that
apply the same entries in any order end with the same rows. `event_row.compaction(group,
row)` drops entries that newer ones make redundant.

Pass `key_type`: without it the key is `object`, so a callback that types its key
(`def remove(key: str)`) doesn't fit the handler and pyright rejects it.

## Journals

`event_journal.layer_memory` keeps entries in memory. `sql_event_journal.layer()` keeps
them in a [SQL](/docs/sql) database (SQLite or PostgreSQL), with local writes serialized
across processes. Entry ids are UUID v7, so the journal is ordered by time.

## Sync with a server

<Diagram name="eventlog-sync" title="Each client writes to its own journal; the remote sends new entries to the server and replays what other clients wrote" />

`event_log_remote.layer_encrypted` and `layer_unencrypted` connect the log to a server
over the [RPC](/docs/rpc) protocol in `event_log_message`. A remote sends what the journal
has not sent yet, in chunks, and replays the server's changes through the handlers,
running `group_compaction` / `group_batch_compaction` compactors on the way in.
`group_reactivity(group, keys)` invalidates `pyfect.reactivity` keys as entries are
handled, so reactive queries rerun.

The encrypted server, `event_log_server_encrypted.layer`, stores AES-GCM batches it cannot
read: only clients holding the identity's key can. The unencrypted one,
`event_log_server_unencrypted.layer(...)`, runs the handlers itself, maps identities to
stores, checks an `EventLogServerAuthorization` and can compact the backlog. Both have
memory storage for tests and SQL storage (`sql_event_log_server_encrypted`,
`sql_event_log_server_unencrypted`). Clients authenticate by signing a challenge with an
Ed25519 key derived from their identity. A challenge lives on its connection for 30 seconds
and is used once. The server binds the first verified signing key of an identity and rejects
any other; `authorize_identity` also receives the presented `signing_public_key`, so a
deployment that records each identity's key at provisioning time
(`event_log_session_auth.derive_signing_public_key`) can reject every other key, even on
first use.

Here a test server and two devices of one user, a laptop and a phone, sync a note. The
server is `event_log_server_encrypted.layer` behind `rpc_server.layer_protocol_websocket(path)`,
served by a router; each device's remote is `event_log_remote.layer_encrypted` over
`rpc_client.layer_protocol_socket()` on a `ws.layer_web_socket(url)`. Both devices write as
the same `Identity`: `encode_identity_string` turns it into text to carry to the other
device, and `decode_identity_string` reads it back.

To wait for a sync, run `log.synced`: it succeeds once the server has acknowledged
everything the log wrote and the log has applied the server's changes up to the latest
entry the server held when asked. Effect has no such call; pyfect adds it (with the
`EventLog.LatestSequence` RPC it asks the server through), so a test or a script can sync
and then check, without sleeping.

Payloads, entries and the write and change frames are
[SchemaBinary](/docs/streams#schemabinary) frames with Effect's bytes.

## Remote compaction

An encrypted server that sets `HelloResponse.compaction` can keep a compacted snapshot of
a store's history, so a new device replays the snapshot and a recent tail instead of every
write. Only clients can decrypt the entries, so clients build the snapshots. A compactor
opts in with `remote=True` on `group_compaction` or `group_batch_compaction`
(`event_row.compaction` always does). That promises what the library can't check: the
entries it keeps depend only on the set of input entries, never on services, the clock or
their order, and compaction composes, so `drop(drop(a) + b)` keeps what `drop(a + b)` keeps
even when `b` holds older entries. A remote run only drops entries: a call that writes a
new entry keeps its whole input, and entries that don't decode, including ones with fields
the schema doesn't know, are kept. Before uploading, the run passes the kept entries through
the compactors again and uploads nothing when that drops more or a compactor dies.

The log polls the compaction status when it connects and about hourly. When the server
wants compaction and the journal has caught up, it starts a background run after a random
delay of one to five minutes: it reads the input (from the journal where it can, fetching
the rest), runs the opted-in compactors and uploads what they keep in segments of about
512 KB. The server lets one run per store hold a stage, so devices that start together
download the input once. `log.compact()` (or `log.compact(remote_id=...)`) runs one now and
returns a `CompactOutcome` per remote. A device with a large store can opt out with
`event_log_remote.layer_encrypted_with(compaction=False)` and leave compaction to a device
with more memory, since a run holds every kept entry in memory.

On the server, both storages compact: `event_log_server_encrypted.layer_storage_memory_with(...)`
and `sql_event_log_server_encrypted.layer_storage(compaction=...)`. A store wants compaction
once at least `threshold_floor` (1000) entries, and at least as many as the active snapshot
keeps, were stored more than `lag` (24 hours) ago. After runs that kept everything, it waits
for that many new entries, doubling the wait after each one. A stage's claim lasts `stage_ttl` (10 minutes) from its last
uploaded part, and a replaced snapshot stays restorable for `grace` (30 days), which must be
longer than both. `storage.compaction.rollback(public_key, store_id, activation_id)` withdraws
the active snapshot and appends its input again at the head, so readers that already passed
the snapshot get every entry. A sweep every `sweep_interval` (1 hour) closes expired stages
and prunes what nothing restorable needs; the SQL sweep resumes a prune that died midway.
