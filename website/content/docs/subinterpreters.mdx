`concurrent.interpreters` is new in Python 3.14: on 3.13, building the layer dies with
`InterpretersUnavailableError`.

On the GIL build, Python code in `fx.blocking` takes turns with every other thread. Python 3.14's
`concurrent.interpreters` runs code in subinterpreters: interpreters in the same process, each with
its own GIL and its own modules, so pure-Python work in them runs on several cores at once without
the start-up, memory and pipes of a `ProcessWorker`. `pyfect.interpreter_pool` runs functions in
them from effects.

Provide a pool with `interpreter_pool.layer(size=...)` (one interpreter per CPU by default; each
starts on first need and closes when the layer is released) and call a function with
`interpreter_pool.call(f, *args)`. A raised exception is a defect; `try_call` fails with an
`UnknownError` around it instead, or with what `catch=` makes of it, as `fx.try_blocking` does.

## What crosses

A subinterpreter shares no objects with yours. The function, its arguments, its result and a
raised exception are copied across:

- A function that reads no globals and closes over nothing, a lambda included, crosses as its
  code, wherever it is defined. It may import what it needs inside its body.
- Any other function crosses by reference: the subinterpreter imports its module, the first time
  it runs something from it, and looks it up by name. Each subinterpreter starts with your
  program's `sys.path`. Keep these functions in a module that imports little: importing `pyfect`
  there takes up to a second. A lambda or a nested function that reads globals or captured
  variables has no name to look up, so the call dies with `NotShareableError`.
- Arguments and results must pickle. Objects the function changes are copies, so return what
  you need instead.
- An exception comes back as itself when it pickles, with the
  `concurrent.interpreters.ExecutionFailed` that describes it (traceback included) as its
  `__cause__`. One that doesn't pickle comes back as that `ExecutionFailed`.

A function that reads globals of the script you ran (`python app.py`, so its module is
`__main__`) is found by running the whole script again inside the subinterpreter. With its
top-level code under `if __name__ == "__main__":`, that re-run only defines the functions, and
the call works. Without the guard, the re-run reaches the script's own `fx.run_blocking` (or any
other run), which dies there at once; the call then dies with
`interpreter_pool.MainScriptRerunError`, which says to add the guard or move the function into an
importable module. Everything the script does before that run happens a second time, in the
subinterpreter: a file it writes is written twice, a message it prints is printed twice. That
re-run is CPython's, so the guard is the fix.

## Interruption

Python can't stop a call that has started. Interrupting the fiber abandons it, as `fx.blocking`
does: a call still waiting for a free interpreter is withdrawn and never runs, while a running
one goes on until it returns and its result is dropped. Releasing the layer fails calls still
waiting with `InterpreterPoolClosedError` and returns once every interpreter has closed, so it
waits for an abandoned call to return: no interpreter outlives its pool, and a call that never
returns keeps the release waiting.

## Memory on the free-threaded build

On CPython 3.14t, creating many short-lived interpreters raises peak memory to a few GB, in CPython
itself rather than in pyfect. Creating 1,000 interpreters, calling each one once and
closing it, with no pyfect involved, took the process to 2.9 GB peak RSS (3.14.7t on macOS), where
the GIL build stayed at 37 MB. The same churn through 250 short-lived pools reached 3.8 GB. Keep one
long-lived pool, provided once near the top of the program, rather than a layer per task.

## What it measured

[`benchmarks/interpreter_pool.py`](https://github.com/tylergibbs1/pyfect/blob/main/benchmarks/interpreter_pool.py)
runs 8 calls of the same pure-Python function (about 80 ms alone) with `concurrency=8`, on an
18-core Apple M-series machine other jobs were also using. The rate is 8 times one call's time
over the fan-out's:

| | 3.14 | 3.14t |
| --- | --- | --- |
| inline (`fx.sync`) | 1.01x | 1.02x |
| `fx.blocking` | 1.02x | 5.60x |
| `interpreter_pool.call` | 7.05x | 6.41x |

The round trip of a call that does nothing, p50 / p95, unloaded:

| | 3.14 | 3.14t |
| --- | --- | --- |
| `fx.blocking` | 0.024 / 0.032 ms | 0.017 / 0.031 ms |
| `interpreter_pool.call` | 0.036 / 0.049 ms | 0.354 / 0.391 ms |

So on the GIL build a pool of subinterpreters is the way to spread pure-Python work over cores
inside one process. On free-threaded 3.14t, `fx.blocking` does it too, with no copying and a
tenth of the round trip, so the pool only pays there for isolation. With a pure-Python loop
spinning on a thread per core, either round trip waits on the OS for a core (3.14t, p95 21 ms
for the pool, 29 ms for `fx.blocking`), and on the GIL build behind every busy thread for the
GIL, hundreds of milliseconds.
