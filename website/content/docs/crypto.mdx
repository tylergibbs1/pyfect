`pyfect.crypto` gives each family of operations its own service: `SecureRandom`,
`Digest`, `Mac`, `Kdf`, `Aead`, `Cipher`, `Signature`, `KeyAgreement` and `KeyWrap`.
Nothing is hand-rolled: the primitives come from `hashlib`, `hmac`, the `cryptography`
package and PyNaCl, installed with the `crypto` extra.

## Services

Provide `native.layer` for every family on the host's libraries, or one of its parts
(`native.layer_aead`, `native.layer_signature`, ...). Each module also has
`layer_web_crypto`, which runs on the `WebCrypto` reference: swap that reference, with
`web_crypto.layer(crypto)`, to run every family on another implementation of the Web
Crypto API, as tests do with a fake that fails on purpose.

Keys belong to one algorithm and are typed by it, so a P-256 key cannot reach an
operation on P-384 and an AES-GCM key cannot reach HMAC. They display redacted, compare
by identity, and refuse to be pickled. A failure is a `CryptoError` whose `reason` says
what went wrong: `InvalidKey`, `InvalidArgument`, `DecryptionFailed`, `NotExtractable` or
`Unsupported`. A tampered message, a wrong nonce or the wrong key all give the same
`DecryptionFailed`, and MAC tags are compared in constant time.

AEAD nonces must never repeat under one key. Draw them from `SecureRandom` for AES-GCM,
or use `xchacha20_poly1305`, whose 24-byte nonces are safe to draw at random for any
number of messages. Feed a `KeyAgreement` shared secret to `Kdf` (HKDF) before using it
as a key, and store passwords with `kdf.argon2id()`.

## Envelope encryption

Seal each message under its own data key and store only that key wrapped under a
key-encryption key: `KeyWrap` with `aes256_kw` (RFC 3394) wraps any secret key and
`unwrap` gives it back as a key of the algorithm you name, so changing the outer key
rewraps a few bytes and leaves the ciphertext alone. Here the outer key comes from a
passphrase through `Kdf` with `kdf.argon2id()` (RFC 9106's second recommended setting,
which needs `native.layer`); a wrong passphrase fails to unwrap with `DecryptionFailed`.

## Sealing to a public key

To encrypt for someone who holds an X25519 key pair, agree on a secret with a fresh pair of
your own and send its public half along. `derive_shared_secret` gives raw bytes, which go
through HKDF (`kdf.hkdf_sha256`, with an `info` naming the purpose) before they become an
`aead.key`; the recipient repeats the agreement with their private key and gets the same key.

## Wrapping to a public key

To send a data key to someone who publishes an RSA public key, wrap it with RSA-OAEP:
`key_wrap.rsa_oaep_sha256` is JWE's `RSA-OAEP-256` (OAEP with SHA-256) and
`key_wrap.rsa_oaep_sha1` is JWE's `RSA-OAEP` (OAEP with SHA-1, for protocols that require it).
Both generate 3072-bit keys. A public key that arrives as a JWK becomes a key with
`key_format.decode_public(key_format.jwk, algorithm, JsonWebKey(...))`, where `JsonWebKey`
comes from `pyfect.crypto.key_format`. The algorithm, not the JWK, picks the hash, and a key
wrapped with one hash does not unwrap with the other: it fails with `DecryptionFailed`.

## Key formats and schemas

`key_format` reads and writes keys as SPKI, PKCS#8, PKCS#1, SEC1, JWK and PEM. The
format's type says which keys it holds and which way it goes: `pkcs1` and `sec1` only
read, and PEM formats take text where DER formats take bytes. `pyfect.crypto.schema`
turns keys into schemas: `CS.MacKeyFromBytes(mac.hmac_sha256)` reads raw bytes (base64
under `config.schema`), and `CS.SignaturePublicKeyFromFormat(format, algorithm)` reads a
format. Secret and private keys are written back only with `allow_encode=True`, and keys
never have a JSON form.

## Tokens

`pyfect.jose` builds JSON Web Signatures, Encryption and Tokens on these services.
`jwk` generates, imports and exports keys and computes thumbprints; `jws` signs with
`HS*`, `RS*`, `PS*`, `ES*` and `EdDSA`; `jwe` encrypts with a shared key; `jwt` signs or
encrypts claims described by a schema and checks them against a policy (`subject`,
`issuer`, `audience`, clock tolerance, ...). `jwks.layer_remote(url)` resolves a token's
key from an issuer's key set, cached and refreshed once for an unknown `kid`. Every
failure is a `JoseError`, and tokens are `Redacted`.

### Expiring tokens

`jwt.sign` signs exactly the claims you give it, so an expiring token carries `iat` and
`exp` itself, as NumericDates in whole seconds, and its claims schema lists them. `verify`
always checks `exp` and `nbf` against the `Clock`; `required_claims=["iat", "exp"]` also
refuses a token without them. To use RFC 7638's thumbprint as the `kid`, compute it from the
generated public JWK and set it on the imported keys with `dataclasses.replace` (they are
frozen dataclasses): `sign` puts it in the header, and `jwk.export_public` writes it into the
JWK you serve.

### Encrypted tokens

`jwt.encrypt` seals claims into a compact JWE that only holders of the shared key can read, as
for a session token the issuing service opens again itself; `jwt.decrypt` opens it and checks
the claims against the same policy options as `verify`. `jwe.encrypt` and `jwe.decrypt` do the
same for any bytes. As in Effect, one algorithm pair is supported: `alg` `dir` (the key is used
directly, so the token's encrypted-key segment is empty) with `enc` `A256GCM`. The key is a
32-byte `jwk.DirKey`, from `jwk.import_dir` of a JWK made with `jwk.generate_secret("dir")`. A
token with any other `alg` or `enc`, such as `A128GCM` (RFC 7520 §5.6), or with a `zip` or
`crit` header, is refused with `InvalidToken`; a wrong key or a tampered token gives
`DecryptionFailed`.

### Key sets that change

`jwks.layer_local(key_set)` reads its key set once. When keys are added or revoked while the
app runs, build the service for each request with `jwks.make_local(key_set)`, or write your own
`JwksService(resolve=...)`: `resolve` gets the token's `Selection` (algorithm, `kid`, header) and
returns the key or fails, here with `KeyNotFound` for a revoked `kid`.
