Effect's cluster runs entities, small stateful services addressed by a type and an id,
across a group of processes called runners. Each entity id hashes to one of a fixed number
of shards, and each shard belongs to one runner at a time, so a message for an entity
reaches the one runner that holds it. Messages can be persisted, so a request survives a
runner restarting, and runners take shards over from each other when one leaves.
`pyfect.cluster` follows Effect's `effect/cluster`; import it as a submodule.

## Entities

An entity type is a subclass of `Entity` whose attributes are [RPCs](/docs/rpc). Its
handlers are built when an entity id gets its first message, and that instance keeps
running, holding its state, until it has been idle for `max_idle_time`. An entity handles
one message at a time unless `to_layer` is given a `concurrency`. `Counter.client()` is an
effect giving a function from an entity id to a client whose methods are the RPCs, with
payload, result and error typed from their schemas; it works the same from any runner.

An RPC annotated `Persisted` is stored before it runs and its reply is stored when it
finishes: a sender waits on the stored reply, a request with the same primary key is
answered once, and a request a runner had not finished when it stopped runs again on the
runner that takes its shard over. A volatile RPC goes straight to the runner and is not
stored: if that runner dies before answering, the sender sends it again to the runner that
takes the shard, so its handler can run twice, as in Effect. Keep volatile handlers safe to
repeat, or annotate the RPC `Persisted`. Handlers read their own address from `CurrentAddress` and their runner's
from `CurrentRunnerAddress`. `to_layer` takes the handlers directly, `to_layer_effect` the
effect that builds them, and `to_layer_queue` gives a mailbox to read messages from instead.
`entity.make_test_client` calls an entity's handlers without a cluster, for unit tests. It
reads `ShardingConfig` to place each entity id on a shard, so provide
`sharding_config.layer()`, as Effect's `makeTestClient` needs it too.

## Shards and runners

A `ShardId` is a shard group and a number. `ShardingConfig` sets `shards_per_group` (300,
as in Effect) and the groups a runner serves. Keep it the same for the life of a cluster:
an entity's shard comes from its id's hash modulo that count. A `Runner` has a
`RunnerAddress`, its shard groups and a weight. Shards are assigned to runners with
`pyfect.hash_ring.HashRing`, a consistent-hashing ring with Effect's exact hash, so a
pyfect ring assigns shards as Effect's would. A runner with weight 2 gets twice the shards.

## Running a cluster

`Sharding` is the service at the center of a runner: it registers entities and singletons,
takes shard locks, routes each message to the runner holding its shard and retries when a
shard moves. Three layers build it with everything it needs:

- `test_runner.layer`: one runner in memory, for tests and examples. It takes its shards on
  the clock, so under the [test clock](/docs/testing) a request waits until the test moves
  time (`testing.adjust("1 millis")` is enough), as in Effect's own cluster tests.
- `single_runner.layer(...)`: one runner whose messages are in SQL, for a single process
  that should still survive restarts.
- `cluster_socket.layer(...)` and `cluster_http.layer(transport="http" | "websocket", ...)`:
  a runner that listens on its `runner_address` and talks to the others over TCP, HTTP or
  WebSockets, with messages and shard locks in SQL (`storage="sql"`, the default), in
  memory (`storage="local"`) or in storage layers you provide (`storage="byo"`). Import
  them on their own (`from pyfect.cluster import cluster_socket`), as Effect keeps them in
  platform-node.

`single_runner.layer()` needs only a `SqlClient`; `sharding_config=` updates the settings it
reads from the environment, and `runner_storage_kind="memory"` keeps the shard locks in
memory. Here a workflow engine runs on it over a SQLite file, and a second run on the same

A runner that stops on purpose (its scope closes, as on a deploy) drains before it hands
over. It lets the requests its entities are running finish for up to
`entity_termination_timeout` (15 seconds, as in Effect, to fit Kubernetes' grace period),
and only then releases their shards. So a job that is running when its runner stops usually
finishes on that runner and is not run again elsewhere. A request still running at the
timeout is interrupted, and a persisted one then runs again on the runner that takes its
shard. With a timeout of 0 the runner hands over at once, as `runners.py` above does so its
example stops quickly. An RPC annotated `cluster_schema.InterruptOnTermination` is interrupted
when the drain starts instead of waited for. A runner that dies (`kill -9`) does not drain:
the others take its shards once they see it is gone, and run its unfinished persisted
requests. They see it is gone when its heartbeat and shard locks are older than
`shard_lock_expiration` (35 seconds, as in Effect) and their next assignment check runs, so
with the default settings its shards move about 35 to 55 seconds after it dies. A lower
`shard_lock_expiration` (kept well above `shard_lock_refresh_interval`, 10 seconds) moves
them sooner.

`sharding_config` takes a function that updates the settings read from the environment.
`client_only=True` makes a runner that sends messages but holds no shards, for a web server
in front of the cluster. `runner_health="k8s"` checks whether a runner that stopped
answering is still alive by reading its pod from the Kubernetes API, where the default
pings it. Messages are [SchemaBinary](/docs/streams#schemabinary) frames, as in Effect;
`serialization="ndjson"` writes newline-delimited JSON instead, and
`serialization_max_buffer_size` limits a frame of either.
Lower level pieces are there too: `socket_runner` and `http_runner` (the protocols and servers), `runner_server`,
`runners` and `runner_health`.

Every runner of a cluster must use the same serialization. A runner can't read the other
format, so health pings between the two fail: the runner that holds the cluster's health
check marks the runners on the other format `healthy = false` in `cluster_runners`, and the
hash ring gives them no shards. Nothing is lost or run twice, but they do no entity work,
and as in Effect this is logged only at Debug ("Runner is unhealthy"), so it looks like a
dead runner. To change serialization, or to upgrade from a pyfect whose default was ndjson,
either replace every runner at once, or roll the upgrade out with `serialization="ndjson"`
set on the new runners and switch every runner to binary later, all at once.

`entity_proxy` exposes an entity as an RPC group or an [HTTP API](/docs/http-api) group, and
`entity_proxy_server` serves it. `to_http_api_group(name, entity)` builds the HTTP group at
run time, so its client has no attribute per operation: read one by name with
`.method("Increment")` or `.method("IncrementDiscard")`, typed `Any`. For a typed client,
declare the operations in a group of your own with `entity_proxy.http_endpoints(Entity.rpc)`,
one line per RPC. RPCs you leave out stay off HTTP.

## Singletons and cron jobs

`singleton.make(name, effect)` runs an effect on exactly one runner of the cluster, the one
holding the singleton's shard, and starts it again on another runner when that shard moves.
`cluster_cron.make` runs a job on a [cron](/docs/schedules#cron) schedule once per instant
across the whole cluster: each run is a persisted message delivered at its instant, which
schedules the next one, so a run is not lost while runners come and go. The job reads its
instant from `CurrentScheduledTime`. With `calculate_next_run_from_previous=True` one entity
runs the instants in order and catches up on missed ones; runs older than
`skip_if_older_than` (a day) are skipped.

Messages due later, like the next cron run or a durable clock's wake-up, are read from
storage when they fall due on the runner that stored them, and by every runner every
`entity_message_poll_interval` (10 seconds, as in Effect), which also finds messages another
runner stored. Under the [test clock](/docs/testing) each poll, shard-lock refresh and
assignment check is a wake-up, so adjusting by days costs real time; adjust by what the test
needs.

## Workflows

[Workflows](/docs/workflows) run on one process with `workflow_engine.layer_memory`.
`cluster_workflow_engine.layer` runs the same workflows on the cluster: each execution is an
entity, its activity results, deferred completions and durable clocks are persisted
messages, and an execution suspended on a runner that stops resumes on the runner that takes
its shard, replaying its completed activities from storage instead of running them again.

## Messages

A message to an entity travels as an `envelope`: a `Request` carrying an RPC's payload, an
`AckChunk` acknowledging a streamed reply, or an `Interrupt`. Replies are `WithExit` (the
final `Exit`) or `Chunk` (part of a stream). Request ids are snowflakes: 64-bit ids made of
a millisecond timestamp, the machine id and a sequence, ordered by time and unique per
machine. Envelopes and replies are stored as Effect's JSON, so the rows pyfect writes
match Effect's.

## Storage

`MessageStorage` persists requests and their replies for at-least-once delivery: it
dedupes requests by primary key, hands unprocessed messages to the runner that holds their
shard, and notifies waiting senders of a final reply after the transaction that stored it
commits (stream chunks at once).
`message_storage.layer_memory` keeps them in memory; `sql_message_storage.layer` uses
Effect's tables on a [SQL](/docs/sql) client (SQLite or PostgreSQL).

`RunnerStorage` registers runners and holds shard locks, so two runners never own one
shard. `runner_storage.layer_memory` is for tests; `sql_runner_storage.layer` takes
PostgreSQL advisory locks on one reserved connection, or leases in a table on SQLite (and
with `shard_lock_disable_advisory`), renewed every `shard_lock_refresh_interval`.

`k8s_http_client.layer` is a Kubernetes API client for runners in a cluster: it reads the
pod's service-account token and lists or creates pods, and `Pod.is_ready` reads a pod's
conditions, which the runner health check uses.
