Effect's cluster runs entities, small stateful services addressed by a type and an id,
across a group of processes called runners. Each entity id hashes to one of a fixed number
of shards, and each shard belongs to one runner at a time, so a message for an entity
reaches the one runner that holds it. Messages can be persisted, so a request survives a
runner restarting, and runners take shards over from each other when one leaves.
`pyfect.cluster` follows Effect's `effect/cluster`; import it as a submodule.

The port is partial. Shards, runner addresses, ids, configuration, envelopes, message
storage and runner storage are here. Entities, `Sharding`, the socket and HTTP runners,
singletons, `ClusterCron` and the cluster workflow engine are not ported yet;
[PARITY.md](https://github.com/tylergibbs1/pyfect/blob/main/docs/PARITY.md) tracks them.
Until then, [workflows](/docs/workflows) run on one process with
`workflow_engine.layer_memory`.

## Shards and runners

A `ShardId` is a shard group and a number. `ShardingConfig` sets `shards_per_group` (300,
as in Effect) and the groups a runner serves. Keep it the same for the life of a cluster:
an entity's shard comes from its id's hash modulo that count. A `Runner` has a
`RunnerAddress`, its shard groups and a weight. Shards are assigned to runners with
`pyfect.hash_ring.HashRing`, a consistent-hashing ring with Effect's exact hash, so a
pyfect ring assigns shards as Effect's would. A runner with weight 2 gets twice the shards.

`sharding_config.layer(settings)` provides settings (start from `dataclasses.replace(
sharding_config.DEFAULTS, ...)`), and `layer_from_env()` reads them from the environment
in CONSTANT_CASE (`SHARDS_PER_GROUP`, `HOST`, `PORT`), with Effect's defaults for the
rest. Durations are [`duration.Seconds`](/docs/reference/duration).

## Messages

A message to an entity travels as an `envelope`: a `Request` carrying an RPC's payload, an
`AckChunk` acknowledging a streamed reply, or an `Interrupt`. Replies are `WithExit` (the
final `Exit`) or `Chunk` (part of a stream). Request ids are snowflakes: 64-bit ids made of
a millisecond timestamp, the machine id and a sequence, ordered by time and unique per
machine. Envelopes and replies are stored as Effect's JSON, so the rows pyfect writes
match Effect's.

## Storage

`MessageStorage` persists requests and their replies for at-least-once delivery: it
dedupes requests by primary key, hands unprocessed messages to the runner that holds their
shard, and notifies waiting senders of a final reply after the transaction that stored it
commits (stream chunks at once).
`message_storage.layer_memory` keeps them in memory; `sql_message_storage.layer` uses
Effect's tables on a [SQL](/docs/sql) client (SQLite or PostgreSQL).

`RunnerStorage` registers runners and holds shard locks, so two runners never own one
shard. `runner_storage.layer_memory` is for tests; `sql_runner_storage.layer` takes
PostgreSQL advisory locks on one reserved connection, or leases in a table on SQLite (and
with `shard_lock_disable_advisory`), renewed every `shard_lock_refresh_interval`.

`k8s_http_client.layer` is a Kubernetes API client for runners in a cluster: it reads the
pod's service-account token and lists or creates pods, and `Pod.is_ready` reads a pod's
conditions, which Effect's runner health check uses.
