The [Model Context Protocol](https://modelcontextprotocol.io) lets an AI application use
tools, resources and prompts that another program serves. `pyfect.ai.mcp_server` serves
them from the same [toolkits](/docs/ai#tools-and-toolkits) a `LanguageModel` uses, and
`pyfect.ai.mcp_client` connects to any MCP server. The server speaks the protocol's
revisions from 2024-11-05 to the stateless 2026-07-28; the client, as Effect's, speaks
2025-11-25 and 2026-07-28 only.

## Serve a toolkit

`mcp_server.toolkit(Calculator)` registers a toolkit's tools, with its handlers' layer
provided. Each tool is listed with its description, its parameters' JSON Schema and an
output schema; `tool.Readonly`, `Destructive`, `Idempotent` and `OpenWorld` annotations
become its hints. Invalid arguments and declared failures come back as tool errors the
model can read, and any other failure as an internal error that leaks no details. The
2025 revisions allow only an object as a structured result, so on them, as in Effect, a
tool whose result is another kind of value, such as a list, sends it as text content only,
with no `structuredContent` and no output schema in its listing.
`mcp_server.resource`, `resource_template` and `prompt` add resources and prompts the same
way, as layers. Each of these layers needs the `McpServer`, so it can't be merged next to a
transport: pass it, or several merged, as the transport's `registrations=`, which builds them
against the transport's server before serving.

A transport layer serves them. `mcp_server.layer_http(name=..., version=..., path=...,
protocols=..., registrations=...)` adds MCP's Streamable HTTP transport to an
[HTTP router](/docs/http-server), with sessions and JSON or Server-Sent Event replies.
`mcp_server.run_stdio(...)` serves on standard input and output until the input ends, for
a server that a client starts as a child process; see
[`examples/mcp_server.py`](https://github.com/tylergibbs1/pyfect/blob/main/examples/mcp_server.py).
It returns when the input ends, so `run_main` exits 0. `mcp_server.layer_stdio(...)` is
Effect's form: the end of input interrupts the fiber that built the layer, so `.launch()`
under `run_main` exits 130, as Effect's does. Put the layer below your other layers with
`layer.provide_merge`. Under `layer.merge` it builds on a fiber of its own, which has finished
by then, so the program keeps running after the input ends, in Effect as well.

## Connect a client

`mcp_client.layer_http(name=..., version=..., url=..., protocol=...)` connects to a server
over HTTP, and `layer_stdio(command=process.make(...), ...)` starts one as a child process.
The `McpClient` then has the server's `server_info` and `instructions`, `list_tools`,
`list_prompts` and `list_resources`, `call_tool(tool, arguments, schema=...)` decoding the
result's structured content, `get_prompt` and `read_resource`. Failures are an
`McpClientError` whose `reason` says which: a tool error, a timeout (60 seconds by
default), a transport or protocol error.

`mcp_client.toolkit(client, prefix)` gives the server's tools as a toolkit with their
handlers, so `generate_text(prompt, toolkit=...)` lets a model call another program's
tools. Each model tool is named `prefix` followed by the server's name for it, joined as
they are, as in Effect: `"docs__"` gives `docs__search`, and `"docs"` gives `docssearch`.
Pass `tools=` a list you approved earlier (from `list_tools`) to bind exactly those
tools without listing them again, and `timeout=` to bound each call. The client's
`capabilities` say what the server offers.

A call's result is the tool result's text. With `result_mode="complete"` it is the whole
`CallToolResult`, and the model gets its content as text and file parts, so an image a
tool returns reaches the model as an image. A tool error from the server (`isError`)
fails the call with `McpClientError` by default. Pass `failure_mode="return"` to give it
to the model as a failed result instead, as a local tool with `failure_mode="return"`
does: the model gets the encoded `McpClientError`, the tool's own result for a tool
error, so it can read "no country has the code 'XX'" and answer. A request that fails,
such as a timeout or a closed transport, goes back to the model the same way.

The server describes its tools, so its hints are not trusted by default.
`trust_annotations=True` copies them (read-only, destructive, idempotent, open-world and
the title) into the tools' annotations. `transform_tool` gets each tool with its
descriptor and returns one derived from it, to ask for approval or add annotations; the
descriptor stays on the tool as `mcp_client.ToolDescriptor`.

### Return failures as plain text

With `failure_mode="return"` the model gets the encoded `McpClientError`, so a tool's
text sits as JSON inside its `reason`, and some models answer that with an empty reply.
The model sees a failure as the tool's failure schema encodes it, so give the tool a
schema that encodes the `McpClientError` as its `message`, the tool's own text for a tool
error. `transform_tool` sets it with `set_failure`: the schema's type is still
`McpClientError`, so the application gets the same error, and only what the model reads
changes. The schema can't decode, because text doesn't carry the whole error.

## Strict tools

A tool annotated `tool.Strict` lists a closed input schema (`additionalProperties: false`
on every object) and the server refuses arguments with unknown keys before the handler
runs, naming each one. Like Effect, it reports the refusal as an error result on
revisions that do so (2025-11-25 and later) and as an `InvalidParams` error before them.

## Logging and protocol checks

A client's `logging/setLevel` sets its session's threshold: log notifications below it are
dropped, and until it sets one the threshold is the `CurrentLogLevel` the server was built
with (Info unless you provide another), so `debug` messages are not sent by default. Handlers run with `CurrentLogLevel` at the session's level
(`notice` is Effect's Info, `critical` and above are Fatal). On 2026-07-28 each request
names its own level in `_meta["io.modelcontextprotocol/logLevel"]`, and gets only the logs
at that level or above, and only the progress of its own `progressToken`.

The HTTP endpoint checks headers before it runs anything, as Effect does: a
`MCP-Protocol-Version` the server does not speak gets a 400 with error -32022 and the
supported versions, and a header that disagrees with the session or with a 2026-07-28
request's `_meta`, `Mcp-Method` or `Mcp-Name` gets -32020. A 2025-03-26 session may send
JSON-RPC batches (over HTTP and stdio); their answers come back as one array. Over HTTP, if
the batch's handlers send notifications, the reply is an event stream: the notifications, then
the array. A cancelled request in a batch gets no answer.

## Subscriptions

On 2026-07-28 a client asks for change notifications with one long `subscriptions/listen`
request. The answer is an event stream that opens with an acknowledgment naming the filters
the server honors (`toolsListChanged`, `promptsListChanged`, `resourcesListChanged`,
`resourceSubscriptions`), then carries only what matches, each with the request's id in
`_meta["io.modelcontextprotocol/subscriptionId"]`. Changes of one kind made in the same
scheduling window go out once. Idle HTTP streams get a comment every 15 seconds.

Each stream has a backlog of 64 notifications. A client that falls that far behind loses
its subscription and nobody else is held up: over HTTP the stream ends, over stdio it gets
`notifications/cancelled` with the request's id. Before 2026-07-28 clients get list changes
unasked and, over stdio, `resources/subscribe`. To turn subscriptions off, pass
`allow_subscriptions=False` to `mcp_server.layer_http`: discovery advertises no list changes
and `subscriptions/listen` is method not found.

## Request-scoped servers

`mcp_server.layer_http_request_scoped` serves 2026-07-28 with each POST's work belonging to
that request, for hosts that end everything with the response, such as serverless platforms.
When the client goes away the handler is interrupted, and handlers see the request's services
over the layer's. Tools, resources, prompts, completions and a request's own progress and logs
work as in `layer_http`. There are no subscriptions or broadcast notifications, DELETE gets
405, and a sessionful revision in `protocols` is a type error.

Sessions are not what lets a tool ask its client something on this revision. A tool or prompt
handler returns `mcp_schema.InputRequired` with keyed requests (`roots/list`,
`sampling/createMessage`, `elicitation/create`), an opaque `request_state`, or both. The client
retries with its answers, which the handler reads from `McpRequestContext`'s `input_responses`
and `request_state`. Requests go out in 2026-07-28's form, so keys it does not carry (such as a
URL elicitation's `elicitationId`) are dropped and a malformed one is error -32603. A request whose capabilities the client did not declare gets a 400 with
error -32021 and the missing `requiredCapabilities`; on earlier revisions a tool's
`InputRequired` is invalid params. A 2026-07-28 HTTP request must also mirror each parameter
annotated `x-mcp-header` in its `Mcp-Param-<name>` header, plain or as `=?base64?...?=`, or it
gets a 400 with error -32020 before the tool runs.

## Skills

The Skills extension (SEP-2640) serves [Agent Skills](https://agentskills.io): a `SKILL.md`
with YAML frontmatter and the files it refers to. `mcp_server.skill(uri, files)` registers
one at `skill://<path>/SKILL.md`, whose last path segment must be the frontmatter's `name`.
Each file becomes a resource, `skills/list` and `skills/get` list the skill with the SHA-256
digest and size of every file, and `resources/directory/read` browses the namespace. The
server declares `io.modelcontextprotocol/skills` once a skill is registered. Registration
fails with `IllegalArgumentError` when the frontmatter is not valid Agent Skills frontmatter,
a path leaves the skill, two skills overlap, or a file's URI is already a resource; a
resource registered later at a skill file's URI is a defect.

The client's skill methods need `extensions={"skills": True}`: `list_skills`, `get_skill`,
`read_resource_directory` and `read_skill_resource`. They call only a server that declares
the extension, and `read_skill_resource` fails with a `ValidationError` unless the bytes
match the listed digest and, for `SKILL.md`, the frontmatter matches the listing. An invalid
listed skill fails `list_skills`, unless `on_invalid_skill` is given: it is told of each one,
which is left out. Every list scan is bounded by `discovery_limits` (100 pages and 10,000
items by default), which `limits=` overrides per call.

## Middleware and visibility

`mcp_server.middleware(fn, provides=...)` runs `fn(effect, options)` around each
`tools/call`, `resources/read`, `prompts/get` and `completion/complete` of the registrations
its `.layer` is provided to. `options` carries the method, the target (a tool or prompt name,
a URI), the payload, the request context, the HTTP headers and the session id. It can provide
services to the handler (named in `provides`, so the layer discharges them from the
registrations' requirements), run before or after it, or fail with an `McpError`, which the
client gets as a JSON-RPC error with that code and message. `.layer_global`, or
`global_=True`, runs it around every request of the server, outside the local middleware;
middleware provided both ways runs once. `a.combine(b)` runs `a` inside `b`, and middleware
provided further out runs outside all of a combination.

`mcp_server.visibility(check)` is middleware that hides registrations per request: where
`check` gives `False` the registration is left out of `tools/list`, `resources/list`,
`resources/templates/list` and `prompts/list`, and a request for it fails as if it were not
registered. It sees what the middleware outside it provides, so combine it inside the
middleware it reads from. On a list only the middleware outside the innermost visibility
runs, once per registration, and its failure fails the list.

notifications arrive on `client.notifications`, and its requests to the client get method not
found.

## Cache hints

On 2026-07-28, list and discovery results carry `ttlMs` and `cacheScope: "private"`, with a
`ttlMs` of 0 unless the transport's `cache_hints=` says otherwise, such as
`{"tools": {"ttl": "1 minute", "cache_scope": "private"}}` for `tools/list`. The kinds are
`discover`, `tools`, `resources`, `resource_templates`, `prompts` and `skills`; `ttl` is sent
in whole milliseconds, rounded down. A hint that can't be sent (negative, infinite, past
`2**53 - 1` milliseconds, unparsable, or not `"private"`) fails the layer with
`IllegalArgumentError`. A hint lets a client keep a list after it changed, and a client
shared between users reuse one user's list for another, so give one only to lists that are
the same for everyone.

## Security defaults

- `mcp_server.layer_http` keeps at most `max_sessions` (1000) sessions and answers 503 when
  they are all in use; a session idle for `session_idle_timeout` (30 minutes) expires. A
  message larger than `max_message_bytes` (4 MiB, and never more than the app's
  `MaxBodySize`) gets a 413.
- A defect in a tool, resource, prompt or completion handler, or in middleware, is logged and
  reported, and the client gets "Internal error" (code -32603); a tool call gets a generic
  tool error instead. A declared failure with a message sends only its message; one without a
  message sends its fields through their JSON codec, as Effect 4.1.2 does, which writes a
  `Redacted` field's value: keep secrets out of a declared failure's fields.
- Replies to the server's own requests (roots, sampling, elicitation) are decoded with their
  result schema; a malformed elicitation reply counts as declined.
- The client reads each server message under `max_message_bytes` (16 MiB by default) and
  fails with a `LimitError` reason past it. JSON nested too deeply to parse is a parse
  error on both sides, not a crash.
