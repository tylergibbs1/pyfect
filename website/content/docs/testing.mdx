pyfect ships a pytest plugin, registered when you install the package. Decorate a generator
test with `@testing.effect` and write it like `@fx.gen`.

## The test clock

`@testing.effect` runs the test with a `TestClock`: time only moves when the test calls
`testing.adjust` or `set_time` (epoch milliseconds, as in Effect), and every fiber woken by a
move runs until it waits again. Tests
of retries, timeouts and schedules are exact and take no real time.

A test that would wait forever fails with `StalledError` instead of hanging, and each test has a
real-time timeout (`@testing.effect(timeout="10 seconds")`, 5 seconds by default) that interrupts it and
runs its finalizers.

### What the test clock waits for

Work handed to another thread takes no virtual time: before `adjust` moves time, and after each
wake-up, it waits for `fx.blocking` and `try_blocking` calls, SQLite and Postgres queries, HTTP
client requests, Redis commands, DNS lookups, writes to a socket or a child process, and the
fibers they resume. A loop of a SQLite write then `fx.sleep("10 seconds")` runs once per `adjust("10 seconds")`.

It does not wait for things that may never come: a socket or WebSocket read, a Postgres `listen` or
Redis `subscribe` notification, a blocking Redis command (`BLPOP`, `XREAD BLOCK`), a message from a
worker (process-worker replies included), a child process's output or exit. A fiber waiting on one
of those counts as suspended, and time moves on without it. When a test needs them answered on time,
run it with `@testing.live`, or provide an in-memory layer of the service in place of the real one.

Work that is still running after `warning_delay` (one second) makes `adjust` warn with
`BusyFiberWarning` and move on. That happens when the work itself waits on the test clock, such as a
request to a server in the same test whose handler sleeps: the request cannot finish until time
moves. Test such a handler without the server in between, or use `@testing.live`.

## Services in tests

`testing.layer_fixture(layer, scope=...)` builds a layer once per pytest scope. A test takes the
fixture as its first parameter, annotated `testing.Services[...]` with what the layer builds;
pyright rejects a test that needs anything else. The test console records what was logged.

More: `@testing.live` (real clock and console), `@testing.effect(asyncio=True)`,
`testing.effect_fixture`, `testing.flaky`, `testing.with_live`, and `assert_exit_success` and
friends, which print the full cause on failure. Run only fast tests with
`pytest -m "not pyfect_live"`.

## HTTP routes in memory

`router.in_memory_client(routes)` gives an `HttpClient` whose requests the routes answer in the same
process, with no socket, so time stays virtual. A streamed response body is not buffered: the client
reads each chunk as the handler writes it and pulls the next only when asked, so a test can read
server-sent events while the handler is still running. A reader that stops early closes the
handler's request scope, and a body never read closes with the test's scope.
`router.layer_in_memory_client(routes)` provides it as the `HttpClient` service instead. As in
Effect's `HttpApiTest`, every failure is a defect of the request, even one a server answers with a
response: a route not found dies with its `HttpServerError`, a payload or path parameters failing
their schema with the schema error, so a test reads them with `.exit()`. A response's cookies are in
its `.cookies`, not in `set-cookie` headers, as in Effect, which hands the server response over
without writing it to the wire.

## Property tests

`@testing.prop(...)` runs a test on many generated inputs, as Effect's `it.prop` does. Each input
is a schema, drawn with `S.to_strategy`, or a Hypothesis strategy. Positional inputs fill the
test's rightmost parameters, and keyword inputs fill the parameters they name. Any parameters left
over are pytest fixtures. A property passes by returning `True` or `None`. Returning `False` or
raising falsifies it, and Hypothesis shrinks the input to the smallest one that still fails. A
plain property that returns an effect or a generator raises `TypeError` (pyright rejects it too),
because it would otherwise pass without running.

`@testing.effect_prop(...)` and `@testing.live_prop(...)` are the effect forms (`it.effect.prop`
and `it.live.prop`). They run the test once per input, each time with a new `TestClock`, `TestConsole`
and `Scope`, and they take a `layer_fixture` the way `@testing.effect` does. A typed failure or a
defect falsifies the property. An interruption, or the `timeout` (real time, for the whole check),
ends the check without shrinking, and finalizers still run.

`runs=` sets how many inputs are tried and `seed=` makes the draws repeatable. When they are
unset, they come from the active Hypothesis settings profile, which plays the role of Effect's
`Arbitrary.configureGlobal`. Property tests need the `pyfect-dev[hypothesis]` extra.

## Checking failures

A failure records annotations in its cause, such as the span it happened in, and they take
part in equality as in Effect. So `exit_ == fx.exit.fail(error)` is false for a failure inside
`with_span` (or a workflow activity), though both sides print alike; pytest then lists each
side's annotations. `testing.assert_exit_fail(exit_, error)` compares by the error alone, and
`testing.assert_exit_failure(exit_, cause)` compares whole causes.
