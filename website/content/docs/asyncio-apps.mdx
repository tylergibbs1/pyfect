---
title: Adopting in an asyncio app
description: "Moving an existing asyncio service, such as a FastAPI app, to pyfect one function at a time."
---

An existing asyncio app doesn't have to move to pyfect all at once. Its handlers can stay
coroutines that run effects through one `ManagedRuntime`, then its routes can move to pyfect's
router mounted inside the app, and at the end pyfect can serve the app, with whatever hasn't
moved yet mounted as an ASGI app.

## One runtime for the app's life

`fx.ManagedRuntime.make(layer)` builds the layer once and runs effects with its services. Make
it in the app's lifespan, so the layer is built at startup and released at shutdown, and run
each handler's effect with `await runtime.run_async(...)`. Effects keep calling the app's own
coroutines through `fx.from_async` (or `fx.try_async`, which turns a raise into a typed error).

The effects' fibers run on the event loop's thread, between the app's own tasks, so a fiber
that computes for a while holds up the whole app as a blocking coroutine would. Put CPU-heavy
work in `fx.blocking` or another process; [Threads and throughput](/docs/threads) explains.

## Errors at the seam

`run_async` takes only an effect with no typed errors left (`Effect[A, Never, ...]`), and the
runtime's layer must not fail either, so pyright flags a handler that forgets an error. Recover
each typed error where the effect meets the app: into a value with `catch_tag`, or run with
`run_async_exit` and turn the error into what the app raises, such as FastAPI's
`HTTPException`. `pyfect.run.unwrap(exit)` gives the value, or raises a defect or an
interruption as an exception.

`errors="all"` to report every problem, as FastAPI's own validation does.

## Sharing layers between runtimes

Runtimes made with one `layer.MemoMap()` share the layers they have in common: such a layer is
built by the first runtime that needs it and released when the last runtime using it is
disposed, as with Effect's `ManagedRuntime.make(layer, { memoMap })`. `router.to_asgi` takes
one too (`memo_map=`), so routes mounted in the app use the same database pool as the handlers
that still run effects themselves.

## Context variables

An effect reads its caller's `contextvars`, as Effect's runs follow Node's `AsyncLocalStorage`,
so a request id set by the app's middleware reaches pyfect code, however many requests run at
once:

- `run_async` and `run_fork` run the effect in a copy of the caller's context. A variable the
  effect sets stays inside the run.
- A forked fiber starts in a copy of its parent's context.
- A coroutine awaited with `from_async` or `try_async` runs in a copy of the fiber's context,
  as an asyncio task does.
- `fx.run_sync` and `fx.run_blocking` run in the caller's own context, so a variable set by
  the effect is still set after it. A `ManagedRuntime`'s `run_sync` and `run_blocking` run in
  a copy, as its `run_async` does. Effect has no such difference, since Node has one thread.

## Routes mounted in the app

`router.to_asgi(routes)` is an ASGI app, so pyfect routes can be mounted inside the existing
app while the rest of it stays as it is. A route's handler can ask for services; the layer's
type then holds `Requires[Service]`, and `to_asgi` only accepts routes whose requirements its
layer builds, so a missing service is a pyright error rather than a 500 on every request.

`routes.pipe(router.provide_request(services))` builds `services` once, when the app starts,
and gives them to every request of those routes, as Effect's `HttpRouter.provideRequest`.
`layer.provide(services)` builds them only for the routes' layer, not for its requests, so
`to_asgi` refuses it. `layer.provide_merge(services)` works too, since the requests run with
the services the layer builds.
Pyright removes a `Requires` only when it can see that the layer builds that service: in a
helper generic in its services' type, such as `def app_routes[RO](services: Layer[RO])`, it
can't, the `Requires` stay and `to_asgi` refuses the routes. Name the services in the
helper's parameter (`services: Layer[Users | Db, E]`), or apply `provide_request` outside the
helper, where the layer's type is known.

A server sends no lifespan to a mounted app: give the host app
`lifespan=lambda _app: pyfect_app.lifespan()`, or the mounted app's layers are built by the
first request and never released.

## Serving with hypercorn

Once most routes have moved, pyfect can serve the app and mount the rest:
`asgi.from_asgi(legacy_app)` as a `"*"` route on `"/*"` answers every path the router doesn't
have. To mount an app under a path, such as a FastAPI admin app at `/admin`, add its route
with `router.prefix_route("/admin")`: the app gets `/admin` as its `root_path`, so its own
routes still match. On a plain `"/admin/*"` route the `root_path` is empty and every route of
the app answers 404. `from_asgi` passes on HTTP requests only, as Effect's `fromWebHandler`
does: a WebSocket upgrade reaches the mounted app as an `http` request, which a FastAPI
WebSocket route answers with 404, so serve WebSockets from pyfect routes
([WebSockets](/docs/http-server#websockets)). The other way, `router.to_asgi` does bridge
WebSocket connections to pyfect routes.

`hypercorn_server.layer(host=..., port=...)` serves on hypercorn (the `pyfect-dev[http2]`
extra), which speaks HTTP/2 in cleartext as well as HTTP/1.1. hypercorn logs no
startup line of its own: the "Listening on" line is `serve`'s, which `disable_listen_log=True`
leaves out.

Each request is logged by `serve`, unless `disable_logger=True`, with the loggers of the context
requests run in, as in Effect, where both use `HttpMiddleware.logger`. For `serve`, that is
what the server's layer is provided with, as `logger.layer(...)` below; for `to_asgi`, it is
the layer `to_asgi` builds, so provide the loggers to that layer.

## Serving over TLS

Each server takes its own TLS settings in `config`, which passes them to the engine, so their
names differ: hypercorn's `config` holds `hypercorn.Config` attributes, `certfile` and
`keyfile`, and then negotiates HTTP/2 with ALPN; uvicorn's holds `uvicorn.Config` arguments,
`ssl_certfile` and `ssl_keyfile`. Stopping a server closes its idle keep-alive connections at
once, over TLS too, as Node's server does.
