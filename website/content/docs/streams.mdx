A `Stream[A, E, R]` emits any number of `A`s, then ends or fails with `E`. Streams are pulled:
nothing runs until a consumer asks for items, so a slow consumer slows the producer down
(backpressure) and memory stays bounded.

Build streams with `stream.make`, `from_iterable`, `range`, `unfold`, `paginate`,
`from_queue`, `from_async_iterable`, `tick`, ... and transform them with methods: `map`,
`map_effect`, `filter`, `take`, `scan`, `grouped`, `zip`, `merge`, `buffer`, `debounce`,
`throttle`, `retry`, `timeout`. The ones that remove an error or a service (`stream.catch_tag`,
`stream.provide`) are functions for `.pipe`, as for effects.

## Batches

`grouped(n)` emits tuples of `n` items (the last may be shorter), as Effect's readonly arrays.
`grouped_within(n, duration)` emits lists and also ends a batch once
`duration` has passed since its first item, so a burst goes out in full batches and a
straggler is not held back waiting for more. Here a queue's items are posted three at a time.

## Rollups

A sink can also run again and again over one stream, each run's result becoming an item.
`transduce(sink)` starts the next run where the last one stopped (its leftovers first).
`aggregate(sink)` does the same on a fiber of its own, so the sink keeps folding while
downstream is busy. `aggregate_within(sink, schedule)` also ends a run when the schedule says
so, which makes a sink that never ends on its own a rollup per window.

The schedule steps once per run, when the run gets its first item, and its clock leaves out the
time between runs, so an idle stream does not run it. `schedule.fixed` and other time-based
schedules therefore count only time spent aggregating; `schedule.spaced` is the flush timer.
When the schedule ends, the current run and the sink's leftovers are emitted and the stream ends.

An upstream failure ends the two differently, as in Effect: `transduce` emits the run in
progress and then fails, while `aggregate` and `aggregate_within` fail at once and drop the
open run.

## A pipeline

NDJSON records arriving in byte chunks, priced by a flaky service four at a time with retries,
buffered so memory stays bounded, batched and written by a sink. `examples/stream_pipeline.py`
in the repository is a longer version.

<include meta='title="pipeline.py"'>../../snippets/streams/pipeline.py</include>

Streams are pulled: nothing upstream runs until the sink asks for more. `map_effect` keeps
at most four calls in flight and `buffer` holds at most eight priced items. With what
`map_effect` holds and the item being handed on, pricing can run about twenty items ahead of a
stalled writer (as in Effect): a fixed bound, so a slow sink slows the whole pipeline instead of
filling memory.

<Diagram name="stream-pipeline" title="The pipeline's stages from byte chunks to the sink, which pulls from upstream" />

Every stage runs on the run's one thread, so a pipeline's throughput is one core's: millions of
items a second for chunked operators, a few hundred thousand for per-item effects, on either
CPython build. [Threads and throughput](/docs/threads) has the numbers, where CPU-heavy steps
belong and how to spot a saturated run.

`fx.encoding` has framers for NDJSON, JSON arrays and Server-Sent Events, and channels for CSV,
XML, zip and tar, below. As in Effect, `ndjson.decode()` fails the whole stream at the first
line that isn't JSON; to skip bad lines, read text lines (`decode_text().split_lines()`) and
parse each one yourself.

## Custom operators

When no operator fits, write one as a `Channel` and run the stream through it with
`pipe_through_channel_or_fail` (or `pipe_through_channel`, whose channel also sees the stream's
failure). A stream's channel reads and writes chunks: non-empty tuples of items.
`channel.from_transform(transform)` builds the channel from a function given the upstream pull
and a scope for resources:

- The upstream pull is an effect that succeeds with the next chunk and fails with `Done` once
  the stream ends (see [`pyfect.pull`](/docs/reference/pull)).
- `transform` returns an effect of the channel's own pull, which works the same way. A `Done`
  from upstream that it lets through ends it too.
- `transform` runs once per run of the stream, so state made inside it belongs to that run.
- Each chunk it writes must be non-empty, as for `stream.from_channel`. The types can't say so
  (Effect's do), so skip a chunk the operator emptied instead of writing it.

## Keys, rates and fan-out

Each operator below matches Effect's, including the rules that are easy to miss.

**Rates.** `throttle(cost=..., units=n, duration=...)` spends tokens from a bucket that refills
`n` per `duration` and holds up to `units + burst`. It starts with `units` tokens, not the
full `units + burst`. `"shape"` delays a chunk until it can pay; `"enforce"` drops it, so a
whole chunk is kept or dropped, never part of one.

**Keys.** `group_by_key(f)` writes `(key, group)` the first time a key appears, with `group`
the stream of that key's items (`group_by` does the same with an effect that gives a key and
a value). Run the groups concurrently, with `flat_map(..., concurrency="unbounded")`. Each
group buffers up to `buffer_size` items (4096 by default), and while one is full the upstream
waits. So one slow group stalls every key. A `buffer` with a `"dropping"` or `"sliding"`
strategy on the slow group keeps the others moving.

**Fan-out.** `broadcast_n(n, capacity=...)` gives `n` streams of the same items, subscribed
before the upstream starts. `broadcast(capacity=...)` gives one stream that many readers can
run, each from the moment it starts (plus the last `replay` chunks). `share(...)` is a
`broadcast` that starts the upstream with its first reader and stops it after its last
(`idle_time_to_live` keeps it running for a later one, which joins it instead of restarting it;
nothing is kept for absent readers, so what the upstream publishes while none is subscribed is
lost, except the last `replay` chunks). All three run in the current scope,
and `capacity` counts chunks, not items. With `"suspend"` (the default) the upstream stays at
most `capacity` chunks ahead of the slowest reader; `"dropping"` and `"sliding"` drop chunks
for a slow reader instead.

None of these operators reports what it drops (the `"enforce"` throttle, a dropping or sliding
`buffer` or broadcast, a sliding `Queue`), and Effect has no hook for it either. To count drops,
compare counts before and after the stage, or use a dropping `Queue`, whose `offer_all` returns
the items it refused. For a sliding `Queue`, number each offer: it drops its oldest items, never
the newest, so once it ends and the reader drains it, the gaps in the numbers taken count every
drop.

## CSV

`pyfect.encoding.csv` reads RFC 4180 records from text (`decode_string()`) or UTF-8 bytes
(`decode()`) split anywhere: rows of cells, or with `headers=True` dicts keyed by the first
record. `decode_schema_string(schema, headers=True)` decodes each record with a schema, and
`encode_schema_string(schema, headers=True)` writes values back; by default columns go through
the StringTree codec, so numbers, booleans and dates need no transformation.

<include meta='title="csv_people.py"'>../../snippets/streams/csv_people.py</include>

A record longer than `max_record_size` (1 MiB by default) fails with a `CsvError` instead of
growing in memory. A column that cannot be one cell, such as a list, raises when the channel is
made.

## SchemaBinary

`pyfect.encoding.schema_binary` writes a schema's values as compact binary frames, with the
same bytes as Effect's `encoding/SchemaBinary`. `to_codec(schema)` is a schema from `bytes`
holding one frame. `parser(schema)` reads concatenated frames from chunks split anywhere, and
`encoder(schema)` writes them, with a string dictionary for a connection when given
`dictionary=True`. `encode(schema)`, `decode(schema)` and `duplex(channel, input_schema=...,
output_schema=...)` are the same as channels for `Stream.pipe_through_channel`.

<include meta='title="schema_binary.py"'>../../snippets/streams/schema_binary.py</include>

<include lang="text">../../snippets/streams/schema_binary.out</include>

Field ids are hashes of their names, so renaming a field changes its wire identity:
`S.String.pipe(schema_binary.field_id(7))` fixes it across a rename. `S.field(S.String, key="primaryKey")`
gives a snake_case attribute Effect's camelCase field, on every wire. A `datetime` is written
in whole milliseconds and a `Duration` in nanoseconds. Python's dates cover years 1 to 9999,
so Effect's dates beyond those fail to read here.

Numbers are varints by default. `schema_binary.int32` and `uint32` write four little-endian
bytes, and `int64` and `uint64` eight; they reject a value out of range instead of wrapping it,
and pay off for hashes and full-range ids. Switching a field between them and `S.Number`,
`S.Int` or `S.BigInt` is not a compatible change. `to_codec_strict(schema)` reads like
`to_codec` but fails on a field, key or union member the schema does not know, where the
default skips it.

Reference: [`pyfect.stream`](/docs/reference/stream), [`pyfect.sink`](/docs/reference/sink),
[`pyfect.channel`](/docs/reference/channel),
[`pyfect.encoding.schema_binary`](/docs/reference/encoding/schema_binary).

## XML

`pyfect.encoding.xml` reads a document as a stream of events, so a large one never has to fit in
memory. `decode_string()` takes text and `decode()` takes UTF-8 bytes. `elements(path)` turns events
back into one small tree per record, and `encode_string()` and `encode()` write events out.

<include meta='title="xml_feed.py"'>../../snippets/streams/xml_feed.py</include>

<include lang="text">../../snippets/streams/xml_feed.out</include>

A reference to an entity the DOCTYPE declares fails with an `"Unsupported"` error instead of
being expanded, so a document cannot read local files or expand into gigabytes; one to an
undeclared entity is a `"Syntax"` error, as in Effect. `max_token_size`, `max_depth` and
`max_element_size` bound what one document can hold in memory.

## Zip and tar

`pyfect.encoding.zip` and `pyfect.encoding.tar` read an archive as a stream of entries, each with a
header and a `body` stream, and write entries back to archive bytes. Bodies are streamed in both
directions, so an archive does not have to fit in memory.

<include meta='title="archives.py"'>../../snippets/streams/archives.py</include>

<include lang="text">../../snippets/streams/archives.out</include>

Read each body before pulling the next entry: a later read fails with `"BodyConsumed"`, and pulling
the next entry skips what is left. `map_effect` is the usual way to do that.

Neither decoder touches the file system, and both return paths as written in the archive. As in
Effect, a path can be absolute or contain `..`, a tar symlink can redirect the entries after it, and
a zip's central directory is not read, so other tools can see different entries. A deflated zip body
can also expand about a thousand times. Before writing entries to disk, reject paths that leave the
target directory and limit how many bytes you read:
