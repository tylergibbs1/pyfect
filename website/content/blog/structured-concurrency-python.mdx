Structured concurrency in Python means one rule: concurrent work can't outlive the code that
started it. When a function returns, everything it started has finished, failed, or been
cancelled, and its cleanup has run. Trio introduced the idea to Python with nurseries, and
asyncio added `TaskGroup` in 3.11. pyfect, a port of [Effect](https://effect.website) to Python
(`pip install pyfect-dev`), builds its whole runtime on it.

This post covers how that looks in practice: running work concurrently with a limit, timeouts,
interruption, finalizers that always run, and resources. It ends with what free-threaded
Python 3.14 does and doesn't change.

## Fibers

Every pyfect effect runs on a fiber, a lightweight thread managed by pyfect's scheduler. You
can run a program with `fx.run_blocking`, with no event loop, or inside asyncio with
`fx.run_async`. The code is the same either way.

`eff.fork()` starts a child fiber and returns at once. The child is tied to its parent: when
the parent finishes, its children still running are interrupted.

The heartbeat loops forever, and nothing in `handle_request` stops it. It stops anyway, when
the request is done, and its `on_interrupt` handler runs. A background task that leaks past
the request that started it, still holding a connection, is a common bug in asyncio code that
calls `create_task` without keeping track of the task. Here it can't happen by default. When
you do want a fiber to outlive its parent, `fork_daemon` says so explicitly.

## Running work concurrently with a limit

`fx.for_each(items, f, concurrency=n)` runs `f` on every item, at most `n` at a time, and
returns the results in input order. `fx.all(a, b, c)` does the same for a fixed set of effects
and keeps each one's type.

## Cancel tasks in Python safely: timeouts and interruption

Cancelling work safely has two halves: the work must actually stop, and its cleanup must run
before the caller moves on. In pyfect, a timeout is an interruption, and `timeout`, `race` and
`race_all` all wait for the interrupted side to finish cleaning up before they return.

`fx.acquire_release` opens the connection and registers its release on a scope, and
`fx.scoped` closes that scope when `report` ends. The query hangs, the timeout fires at 50 ms,
and by the time `run_blocking_exit` returns, the connection is closed. The release function
gets the `Exit`, so it can tell a clean finish from a failure or an interruption, for example
to roll back a transaction instead of committing it.

Three rules make this dependable:

- Interruption is not an exception. In asyncio, cancellation is a `CancelledError` raised into
  your code, and a bare `except:` or a retry loop catching `BaseException` can swallow it. In
  pyfect, error handlers such as `catch_all` never see an interruption, so a handler can't
  swallow one by accident.
- Acquiring a resource can't be interrupted halfway. Either the acquire finished and the
  release will run, or it never started.
- Finalizers run in reverse order of acquisition, as they would in nested `with` blocks.

When a few steps must not be interrupted halfway, wrap them in `fx.uninterruptible_mask`: an
interruption then waits until they are done.

Inside the block, Ctrl-C or an asyncio cancellation counts as an interruption of the scope,

pyfect. The exception still propagates out of the `with`. The

## What free-threaded Python 3.14 changes

Free-threaded CPython (the 3.14t build) can run Python code on several threads at once without
the GIL. It's easy to assume that makes fibers run in parallel. It doesn't, and it's worth
being precise about why.

All the fibers of one pyfect run take turns on that run's thread, as Effect's fibers take
turns on Node's one thread. That is a design choice, not a GIL limitation, and it's what makes
the guarantees above simple to reason about. The [threads guide](/docs/threads) says plainly
that the free-threaded build is no faster for fiber throughput.

What 3.14t speeds up is work pyfect hands to other threads:

- `fx.blocking(f)` and `fx.try_blocking` run a function on a thread pool. On the GIL build,
  Python code there takes turns with your run's thread. On 3.14t it runs at the same time.
  Interrupting the fiber abandons the thread; it can't stop it.
- `fx.on_thread(eff)` runs a whole effect as a run of its own on a new thread. On 3.14t,
  several of them use several cores:

Unlike `fx.blocking`, an effect under `on_thread` can be interrupted: interrupting the caller
interrupts the effect on its own run and waits for its finalizers, so a timeout around it
still cleans up. The [parallel effects guide](/docs/parallel) has measurements of when it pays
off and when the cost of a new run outweighs it.

When several runs on different threads share state, pyfect's shared types (`Ref`, `Queue`,
`Semaphore`, `Deferred`, `Pool` and others) keep each operation atomic across them. On 3.14t
those threads really do run at the same time, which surfaces races the GIL hides. pyfect's CI
runs a cross-thread stress test and the runtime's test suites on 3.14t for that reason, and the
library's extras are chosen so that none of them turns the GIL back on.

So the honest summary: on 3.14t, structured concurrency in pyfect works the same as on the
regular build, and CPU-heavy work you move to `fx.blocking` or `fx.on_thread` can now use more
than one core. On the regular build, the way to use more cores is a worker process.
